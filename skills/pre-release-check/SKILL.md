# 发布前检查（Preflight）

**这个 Skill 的目的是防止「本地一切正常，发出去全部炸」。**

管的是「推上线 / 交出去之前」的九道关，逐条出实测数字。
它不修东西——发现红项，先报告「哪条红 + 实测证据 + 我判断的原因」，等确认后再动手。

配套脚本：`scripts/preflight.js`（零依赖 Node，一条命令跑完九条）。

---

## 一、五条元规则（决定这个 Skill 会不会虚报通过）

| # | 规则 | 为什么 |
|---|---|---|
| R1 | 每条结论必须带**实测数字**（状态码、字节数、条数、行号） | 「正常」「应该没问题」无法被人独立复核 |
| R2 | 结果只有三态：**PASS / FAIL / MANUAL**。`MANUAL` 单独计数，**不算进通过数** | 防止拿人工项凑数把数字刷绿 |
| R3 | 有任意 FAIL 时脚本**退出码为 1** | 红项存在而进程返回成功，就是虚报 |
| R4 | 查不动了（超时、命令不存在、网络断）记 **FAIL(reason)**，不记 PASS | 「没查到」≠「查过且没问题」 |
| R5 | 每轮跑完必须能回答：红了几条、哪几条、证据是什么 | 说不清等于没跑 |

## 二、九条检查项

| # | 层 | 检查项 | 过线标准 |
|---|---|---|---|
| 1 | 安全 | 密钥不进仓库 | 跟踪文件里 0 处命中密钥模式 |
| 2 | 安全 | 敏感文件被正确忽略 | `git check-ignore` 命中 `.env`，并打出**命中的是哪条规则** |
| 3 | 上线 | GitHub Pages 首页可开 | HTTP 200 |
| 4 | 上线 | 静态托管与本地**逐文件**一致 | 5 个前端文件字节数全等 + 去 CR 后哈希一致 |
| 5 | 上线 | 接口链路活着 | HTTP 200 + `data.books` 数组 + 条数 > 0 + 11 个字段齐全 |
| 6 | 数据 | 迁移与代码对齐 | 建临时书 → 删它 → 回 `softDeleted:true` → 再删报「不存在」→ 列表里消失 |
| 7 | 卫生 | 临时测试文件没误入仓库 | `_*_test.js`、`_smoke.html`、`day*-verify/`、`*.zip`、`*.log` 全 0 命中 |
| 8 | 卫生 | 已全部推送 | 先 `fetch`，再 `rev-list --left-right --count main...origin/main` = `0 0` |
| 9 | 卫生 | 不引外部 CDN | `<script src>` / `<link href>` / `<img src>` / `@import` / `url()` 里 0 个 `http(s)://` |

**两条人工项（脚本固定输出 MANUAL，永不计入通过）**：

| # | 检查项 | 为什么必须人眼 |
|---|---|---|
| M1 | 手机宽度不横向溢出、观感不挤 | 脚本量不出「挤」 |
| M2 | Tab 键能走完主要流程，聚焦圈可见 | 迷你 DOM 模拟不了真实焦点顺序 |

## 三、怎么跑

在仓库根目录（`whale-fall-letters/`）执行：

```bash
node skills/pre-release-check/scripts/preflight.js
```

常用变体：

```bash
node skills/pre-release-check/scripts/preflight.js --only 1,2      # 只跑指定几条
node skills/pre-release-check/scripts/preflight.js --md docs/skill-runs/2026-10-21.md   # 同时写一份 markdown 报告
```

退出码：`0` = 无 FAIL（人工项未查也算 0，但汇总里会写明「人工 2 条待办」）；`1` = 有 FAIL；`2` = 脚本自身崩了。

### 轮次（DRAFT / FINAL）

脚本会先看工作区干不干净，自动标注轮次：

| 轮次 | 条件 | 第 8 条的含义 |
|---|---|---|
| **DRAFT** | 有未提交改动 | 第 8 条**必然红**，属预期——东西还没提交完，谈不上「已推送」 |
| **FINAL** | 工作区干净 | 这才是真的发布前状态，第 8 条必须 `0 0` |

**所以正确用法是：先 DRAFT 跑一遍把问题清掉 → 提交推送 → 再 FINAL 跑一遍，全绿才算发出去。**

## 四、反向验证（证明它不会虚报通过）

新写一条检查、或改了脚本逻辑之后，**必须做这个动作再相信它**：

1. **基线跑**：当前状态跑一遍，记下红的哪几条。
2. **故意弄坏一处**：挑一个能被自动检测的点动手（见下表）。
3. **再跑**：对应那条必须**变红**，且证据里能看到你刚改的东西（行号 / 字节差）。
4. **还原**：撤销改动。
5. **三跑**：必须变绿回来。

第 3 步如果还是绿的 → 这条检查是**摆设**，不是「项目没问题」。第 5 步如果不绿 → 它是「常量红」，同样不可信。

两个验证过的植入点：

| 打哪条 | 怎么弄 | 期望 |
|---|---|---|
| ① 密钥 | 在 `community.js` 顶部临时插一行假密钥 `var DEMO_KEY = "sk-live-XXXXXXXXXXXXXXXX";` | 第 1 条红，报出 `community.js:行号` |
| ② 上线一致 | 改 `community.js` 里任意一个字的文案，**不上传** | 第 4 条红，报出「本地 120448 / 线上 120447」这类字节差 |

## 五、坑（这份清单管的东西真踩过的）

- **静态托管是手动上传的，`git push` 不动它。** Day 24 血案：本地改了、提交了、推送了，线上还停在 Day 17。所以第 4 条查的是「静态托管」，不是 GitHub Pages。
- **迁移 SQL 必须先跑，再部署函数。** 反了报 `column is_deleted does not exist`，检查台整页读不出数据。第 6 条就是查这个顺序有没有跑对。
- **接口返回的字段叫 `is_deleted`（下划线），不是 `isDeleted`。** 这跟其他驼峰字段不统一，是历史原因，按实测来，别按直觉猜。
- **网关只映射 `/api/books` 前缀。** 探针路径写成 `/api/no-such-path` 会回 `INVALID_PATH`——那测的是网关，不是函数，别当成「函数挂了」。
- **本机开着 Watt Toolkit 时 curl 必须加 `--ssl-no-revoke`。** 它做 TLS 中间人，不加就报 `CRYPT_E_NO_REVOKE_CHECK`。
- **第 6 条会往真库写一行。** 临时书书名统一 `preflight-<时间戳>` 前缀便于识别，脚本用 `try/finally` 保证验完必删；但如果你中途 Ctrl+C，去数据编辑器看一眼有没有残留。
- **第 2 条命中 `*.env` 这种宽规则时只是提示，不算红。** 宽规则能挡住 `.env`，但连 `.env.production` 之类也一并挡了，以后加新环境变量文件容易看不懂为什么没生效。
- **别用 `git add -A`。** 工作区根有一堆 `_*_test.js`、`day*-verify/`、`.temp/`，第 7 条就是防这个的。

### 检查脚本自己也会骗人（Day 25 写这版时连踩五个）

这几条的教训比检查项本身更重要：**检查报红，先怀疑检查自己瞎了，再怀疑项目。**

1. **`curl -w` 只输出你写在里面的东西。** 原文写成 `-w "\n__STATUS__"` 漏了 `%{http_code}`，状态码永远解析成 0 —— 接口明明 200 返回了 5 本书，第 5 条却报「连不上」，第 6 条还顺手在真库留了垃圾。写 `-w` 时把 `%{http_code}` 和分隔符一起写死。
2. **先抢 id、再判状态。** 第 6 条原先是「状态码不对就 return」，临时书的 id 还没赋给变量就返回了，`finally` 里没东西可删 → 真库留下一本 `preflight-*`。现在改成「只要 body 里能拿到 `book.id` 就先存下来」，状态判断放后面。
3. **业务失败一律 HTTP 200 + `{ok:false, error}`。** 这是 `send()` 里固定 `writeHead(200)` 的既定契约。第 6 条原按「第二次删除应该 404」判定，接口明明回了「这本书不存在」却被判 FAIL。**判业务结果看 `ok` 字段，不看状态码。**
4. **`sk-` 正则要含连字符。** 第一版写成 `sk-[A-Za-z0-9]{16,}`，而真实密钥几乎都是 `sk-live-…` / `sk-proj-…` 这种分段格式，`-` 不在字符集里 → 一个都扫不到。现已改成 `sk-[A-Za-z0-9_-]{16,}`。
5. **文档里的演示密钥会把检查自己扫红。** 这个 Skill 和它的验证记录为了讲清「怎么故意弄坏」，难免写出示例密钥；提交后跑 FINAL 轮，第 1 条会把它当成真泄露。规则已加占位符跳过（连续 `X`、`REDACTED`、`EXAMPLE`、`…`），文档里演示值统一写 `sk-live-XXXX…` —— **写文档时也请照这个写法**。

对应到规则：**脚本自身崩溃走退出码 2，项目有问题走 1** —— 两者不能混成一个 1，否则你分不清「检查器坏了」和「项目坏了」。

## 六、边界（这版故意不做）

- **不做自动化流水线**：不接 Git hook、不接 CI、不定时跑。只做「人手动跑一次」。要自动化是下一步的事，别顺手加。
- **不改代码**：红了就报告，等确认再修。
- **不碰控制台**：不问「传好了吗」，直接比对线上文件的字节与哈希。
