# 数据库备份与恢复

> 这份文档要解决的问题只有一个：**万一数据没了，怎么弄回来。**
> 写于 Day 31。在此之前，项目**零备份** —— 一次手滑的 `DELETE` 就够把两周的数据清零。

---

## 一、两条路，先走第一条

### 路线 A：平台备份（优先，但要先确认有没有）

CloudBase 的 PG 备份由**底层腾讯云 PostgreSQL 实例**提供，控制台里通常有「备份」页签。

**怎么确认：**

1. CloudBase 控制台 → **PostgreSQL** → 选中你的实例
2. 找 **「备份」/「备份与恢复」** 页签
3. 看有没有「自动备份」的记录

**两种结果：**

| 看到什么 | 怎么办 |
|---|---|
| 有自动备份记录 | ✅ 用它。默认每天备份、保留若干天（以控制台为准） |
| 没有这个页签，或显示"暂不支持" | 体验版/共享实例的常见情况 → **走路线 B** |

⚠️ **平台恢复有个关键特性**：恢复时**不会覆盖**当前业务库，而是**恢复到一个新库**（名字形如 `postgres_xxxbak20261027...`）。也就是说恢复完你还得把数据从新库搬回业务库 —— **这一步是真的技术活，所以下面路线 B 的价值不只是"多一份"，而是"你自己能搬得动"。**

---

### 路线 B：逻辑备份（一条命令，自己能搬）

`tools/backup-pg.js` 通过 PG HTTP API 把七张表全量导成一份 JSON。

#### 跑之前：先拿到密钥

1. CloudBase 控制台 → **云函数** → 任选一个（比如 `books`）→ **函数配置** → **环境变量**
2. 复制 `PG_API_KEY` 的值

⚠️ **别复制到记事本再手打** —— 这项目在这上面栽过一次（把 `l` 抄成 `i`，白查两周）。直接复制粘贴。

#### 跑

在仓库根目录：

```bash
# macOS / Linux / Git Bash
PG_API_KEY=你的密钥 node tools/backup-pg.js
```

```powershell
# Windows PowerShell
$env:PG_API_KEY="你的密钥"; node tools/backup-pg.js
```

输出长这样：

```
开始备份 → backups/backup-2026-10-27-20-52.json
  users          3 行
  books          2 行
  notes          1 行
  posts          1 行
  comments       2 行
  messages       1 行
  sessions       4 行

✓ 备份完成：12.4 KB，耗时 1.8s
```

#### 三个安全设计（都是踩过的坑换来的）

1. **任一张表失败，整份备份不写文件。**
   半份备份比没有更危险 —— 你会以为有备份，真出事时才发现少了关键表。
2. **`backups/` 在 .gitignore 里。**
   这个文件含 `passwordHash`、`salt`、会话 `token`。**一旦进了 Git 历史，删都删不干净。**
3. **分页拉取（每次 1000 行）。**
   PostgREST 单次返回有上限，不分页会**静默截断** —— 表格看起来正常，实际少了一半数据。

#### 存哪儿

**别只存在项目目录里。** 和代码放同一个地方，磁盘一坏两个一起没。请至少另存一份到 U 盘或网盘。

## 二、恢复：三种情况，三种做法

> 恢复永远比备份难。下面按"破坏程度"从轻到重排列。

### 情况 1：误删了几条记录（最常见）

**不用恢复整库**，直接从备份文件里把那几行捞出来重新插入即可。

备份是标准 JSON，长这样：

```json
{
  "meta": { "createdAt": "...", "tables": [{ "表": "books", "行数": 2 }] },
  "data": {
    "books": [
      { "id": "book-mvq...", "title": "活着", "userId": "user-...", ... }
    ]
  }
}
```

捞一行的方法：用编辑器打开文件，搜书名/用户名，把那个对象复制出来，
然后 `POST` 回 `/v1/rdb/rest/books`（body 就是那个对象）。

> 也可以用接口 `POST /api/books` 加回去，但要注意：**接口会重新生成 id**，
> 笔记会因此挂空。整行原样写回才保得住 `id`，所以优先用原始 API 而不是业务接口。

### 情况 2：整张表被清空

把备份里那张表的数组，逐行 `POST` 回 `/v1/rdb/rest/<表名>`。

⚠️ **有依赖顺序**，必须按这个顺序写回：

```
users → books → notes → posts → comments → messages → sessions
```

理由：
- `notes` 挂在 `books` 上，书先到
- `posts`/`messages` 的作者是 `users`，人先到
- `sessions` 最后（它引用 users）

虽然没建物理外键、数据库不会拦你，但顺序错了会导致"笔记挂空、帖子里的人查不到"。

### 情况 3：整库误删（最坏）

1. **先停手** —— 别再对数据库做任何写操作
2. **先导出当前状态**（哪怕它是坏的）：跑一次 `tools/backup-pg.js`，
   保留现场。很多人在这里直接把坏的也覆盖掉，反而失去了"哪些是误删、哪些是本来就没有"的判断依据
3. 按情况 2 的顺序把七张表全量写回
4. 写回后**逐表核对行数**，和备份文件 `meta.tables` 里的数字对一遍

## 三、恢复演练：不做这一步，等于没有备份

**备份只有在你成功恢复过之后才算真的存在。**

建议每月做一次轻量演练（10 分钟）：

1. 跑一次备份，记下 `books` 有几行
2. 随便建一本测试书，标题写 `restore-drill-<日期>`
3. 删掉它（软删）
4. 从备份文件里把它捞出来，原样写回
5. 确认列表里它回来了、`id` 没变

第 5 步的"id 没变"是关键 —— 如果 id 变了，说明你走的是业务接口而不是原始写回，那么挂在这本书下的笔记已经全部失联。

## 四、还缺的一块（诚实记录）

- **没有自动化**：目前靠手动跑脚本。真正的自动备份要一个定时任务 + 一个能存密钥的地方，
  这件事还没做。
- **没有异地存储**：备份默认落在 `backups/`，需要人工另存。
- **恢复已脚本化**：`tools/restore-pg.js` 可以把备份里的行原样写回（连 id 一起），
  支持 `--table` / `--id` / `--dry-run` / `--all`。用法见下面「五」。
- ⚠️ **备份有"保鲜期"**：`backups/` 里可能同时躺着好几份，日期不同的内容也不同
  （比如清理了测试数据之前的备份里还有那些垃圾）。**恢复前先看文件名和 `meta.createdAtBeijing`，
  确认拿的是想要的那一份。** 演练时尤其容易踩这个坑。

## 附：七张表都是什么

| 表 | 存什么 | 丢了会怎样 |
|---|---|---|
| `users` | 账号（含密码散列、盐） | **所有人都登不上**，且密码无法还原（散列不可逆），只能重新注册 |
| `books` | 书单（按 userId 隔离） | 每人书单清空 |
| `notes` | 读书笔记（挂在 bookId 上） | 笔记全丢；书还在但笔记没了 |
| `posts` | 论坛帖子 | 帖子全丢 |
| `comments` | 评论（挂在 postId 上） | 评论全丢，帖子变空 |
| `messages` | 私信 | 私信全丢 |
| `sessions` | 登录会话（7 天有效） | 只是**所有人掉线，重新登录即可** —— 这张丢了不可怕 |

**从上往下，越靠上越致命。** `sessions` 是唯一一张丢了无所谓的表 ——
这也是为什么整库恢复时它放在最后写回。

## 五、恢复脚本怎么用

```bash
# ① 先预览（强烈建议每次都先 dry-run）
PG_API_KEY=xxx node tools/restore-pg.js --table books --id book-xxx --dry-run

# ② 真写回某一行（演练用）
PG_API_KEY=xxx node tools/restore-pg.js --table books --id book-xxx

# ③ 写回整张表
PG_API_KEY=xxx node tools/restore-pg.js --table books

# ④ 整库重建（按 users → books → notes → posts → comments → messages → sessions 的顺序）
PG_API_KEY=xxx node tools/restore-pg.js --all
```

参数说明：

| 参数 | 作用 |
|---|---|
| `--file <路径>` | 指定备份文件；不传就取 `backups/` 里**文件名最大**的那份 |
| `--table <表>` | 只处理这张表 |
| `--id <id>` | 只处理这一行（要配合 `--table`） |
| `--all` | 七张表全恢复，按依赖顺序 |
| `--dry-run` | 只打印将要写什么，一个字节都不写 |

**两个设计说明：**

1. **遇到 409（这一行已存在）算"跳过"而不是"失败"。** 恢复时重复写同一行是常态，
   不该因为这个中断整批。
2. **写入是按行 POST，不是批量。** 慢一些，但哪一行失败一眼看得见 ——
   整库恢复时，"悄悄少了一半"比"慢"可怕得多。
