# 数据互通方案（第一步：书单接真库）

> **要解决的问题**：现在书单和笔记存在浏览器本地，换台手机就没了。
> **本方案只管一件事**：让「书」跨设备可见。
> **本方案不做**：账号、权限、私信、笔记跨设备——那是后面三步（见文末）。

---

## 一、先看成本：为什么不能直接「把 localStorage 换成 fetch」

`store.js` 现在是**同步**的：

```js
var res = Store.listBooks();   // 立刻拿到结果
if (res.ok) { ...渲染... }
```

`app.js` 里这样的调用有 **15 处**（`grep -c "Store\." app.js` 实测）。一旦把内部改成 `fetch`，`Store.listBooks()` 只能返回 Promise，**这 15 处全要改成异步回调**，每处都要处理「加载中 / 失败 / 重试」。改完 `app.js` 基本重写一遍。

所以有两条路：

| | 方案 A：本地优先 + 后台同步 | 方案 B：全部改异步 |
|---|---|---|
| `app.js` 改动 | **0 行** | 15 处全改，含加载态与错误态 |
| 界面响应 | 立刻（读本地），后台补云端 | 要等网络，得加 loading |
| 断网时 | 照常用，改动排队 | 基本不可用 |
| 多设备冲突 | **有**：两台同时改同一本，后写覆盖先写 | 同样有（取决于是不是加版本号） |
| 实现难度 | 中（新增一个文件，不动现有文件） | 高（重写渲染层） |
| 可回退 | 容易（一个开关关掉） | 难（改动面太大） |

**选 A。** 理由不只是省事：你 Day 5 的 `docs/TECH_DESIGN.md` 定了「`store.js` 是唯一读写存储的地方」，方案 A 正好**顺着那个设计走**——在它下面垫一层同步，上层一行不用动。方案 B 等于推翻当初的分层。

---

## 二、方案 A 怎么跑

```
   app.js / community.js          ← 一行不改，照常调 Store.xxx()（同步）
            │
        store.js                   ← 一行不改，继续读写 localStorage（离线缓存）
            │
        sync.js  （新增）          ← 唯一的新东西
            │  ↑ 启动时 pull()：GET /api/books → 覆盖本地缓存
            │  ↓ 写操作后 push：POST / PATCH / DELETE → 云端
            │
     /api/books（已有，不用改）
```

关键点：**本地是缓存，云端是真相。**
启动时从云端拉全量写进 localStorage，页面照常同步读。所以换手机时，云端有 → 本地就有。

### 写操作的顺序

1. 先写 localStorage（界面立刻有反馈，跟现在一模一样）
2. 再异步发请求到云端
3. 失败了怎么办：**回滚本地那一次改动**，并提示「没同步上去，请检查网络」
   —— 不能像现在这样「存上了但其实没存上」，那正是 AC-23 要防的事

## 四、首次迁移（这一步不做，你现有的书会“消失”）

云端库里现在有 5 本公共书（三体 / 活着 / 人类简史 / 小王子 / 国境以南）。你手机上也有自己记的书。

如果直接 `pull()` 覆盖本地，**你手机里的书就没了**。所以第一次必须走迁移：

1. 读本地 `reading:books`
2. 逐条 `POST /api/books`（接口自带重名校验，重复的会返回「这本书已经在书单里了，不用重复添加」，跳过即可）
3. `GET /api/books` 拉全量 → 写回本地缓存
4. 打标记 `reading:sync-migrated = 1`，以后不再重复迁

**这是不可逆操作**（会把本地书推到云端），所以：
- 迁移前先导出一份本地 JSON 到文件（`reading:books` 的全部内容）
- 迁移只在开关打开、且标记不存在时执行一次
- 迁移过程每一步都打日志，失败停在原地，不删本地任何东西

## 五、验收（两台设备，缺一不可）

| # | 操作 | 期望 |
|---|---|---|
| 1 | 手机 A 打开页面，等 2 秒 | 看到自己原来那几本（迁移成功） |
| 2 | 手机 A 添加一本「跨设备测试」 | 卡片立刻出现（本地先写） |
| 3 | **手机 B**（另一台设备/另一个浏览器）打开页面 | **看到「跨设备测试」** ← 这就是今天要的那一下 |
| 4 | 手机 A 把它改成「在读」 | B 刷新后也是「在读」 |
| 5 | 手机 A 删掉它 | B 刷新后消失 |
| 6 | 手机 A 断网，添加一本 | 提示「没同步上去」，且本地可见（不算丢） |
| 7 | 恢复网络，刷新 | 那本自动补传上去 |

第 6、7 条是这套方案的价值所在，也是最容易做假的地方——**必须真断网试**。

| 不解决 | 为什么 | 什么时候做 |

## 八、迁移怎么跑（已实测通过）

### 8.1 代码已经就位

| 文件 | 做了什么 |
|---|---|
| `store.js` | 新增两个**受控**写入口：`replaceBooks(list)` / `replaceNotes(list)`。界面代码不该调，它们会整体覆盖。放在 store.js 里，是为了守住「碰存储的地方只有一个」这条（第 9 行那条约定） |
| `sync.js` | 新增 `migrateLocal()`：先下载备份 → 逐条 POST → 拉全量回写 → **笔记 id 重映射** → 打标记 |
| `index.html` | 加一行 `<script src="sync.js"></script>`。**默认关闭，不会自动发任何请求** |

### 8.2 实测发现的两件事（都很关键）

**① 笔记会“消失”——必须重映射。**

迁移前书的 id 是本地生成的 `book_xxxxx`，迁移后被云端 id（`book-mvpa…`）取代。
笔记里存的还是旧 id，于是详情页按新 id 查 → **一条都查不到**。
数据没丢，但用户看到的是「我的笔记全没了」——**这比报错更让人慌**。

所以 `migrateLocal()` 里加了一步 `remapNotes()`：靠**书名 + 作者**把旧 id 映射到新 id。
配不上的（那本书没迁上去）记为 orphan，**原样保留，不删**。

**② 时间戳不保留（实测）。**

```
POST {"status":"reading", ...}
→ "startedAt": null        ← 后端 POST 不会自动补
→ "createdAt": "2026-10-26T13:19:37.418Z"   ← 变成迁移那一刻
```

`totalPages` / `currentPage` / `status` / 书名 / 作者都保留，**但「什么时候开始读的」会丢**。
这是接口设计决定的（POST 只收 6 个字段），要保住得改后端，本次不做，**如实写在迁移报告里**。

### 8.3 操作步骤（你在浏览器里做，我碰不到你的 localStorage）

1. 打开站点（**先备份再动手**，代码会先自动下载一份 JSON 备份）
2. 按 F12 打开控制台，粘这三行：

```js
await Sync.fetchAll().catch(e => console.log(Sync.describeApiError(e)));  // 先确认能连上
```
```js
Sync.enable();
const r = await Sync.migrateLocal();
console.table({ 总数: r.total, 新建: r.created.length, 已存在: r.existed.length,
                失败: r.failed.length, 拉回: r.pulled,
                笔记: r.notesTotal, 重映射: r.notesRemapped, 孤儿: r.notesOrphan });
```

3. 该看到：
   - 浏览器下载一个 `reading-books-backup-<时间戳>.json` ← **这个文件别丢**
   - `新建` = 你本地独有的书，`已存在` = 云端本来有的（同名同作者）
   - `失败` 必须是 0；**不是 0 就停下来**，本地缓存不会被动
4. 刷新页面，确认书和笔记都在

|---|---|

| 笔记还在，但「开始阅读时间」空了 | 见 8.2 ② |

### 8.5 自测覆盖（`day28-verify/sync-v1-migrate-test.js`，36 项全过）

- `replaceBooks` / `replaceNotes` 拦住非数组入参
- `remapNotes` 纯逻辑 6 项：映射 3 条、孤儿 1 条保留、字段不动、不改入参

## 九、写路径与接线（A 步，已完成）

### 9.1 怎么做到 `app.js` 一行不改

`Sync.installHooks()` 把 `Store.addBook / updateBook / deleteBook` **包一层**：

```js
S.addBook = function (input) {
  var r = origAdd(input);          // ① 先照原样同步执行 —— 界面立刻有反馈
  if (r && r.ok) pushAdd(r.data)   // ② 再异步推云端
      .then(null, function (e) { report(e, '添加'); });
  return r;                        // ③ 同步返回，app.js 感觉不到区别
};
```

- 成功：服务端返回的书会**替换本地那条**，把本地 id（`book_xxx`）换成云端 id（`book-mvpa…`）
- 失败：**本地回滚** + 记 `status.lastError` + 调 `onError` 回调
- 串行队列：连点三次不会并发，也不会串号

### 9.2 踩到的坑：回滚不能被自己的监听器捕获

第一次自测就红了，`onError` 报的是「删除」，可那一段只调用了「添加」。

原因：`pushAdd` 失败后调 `Store.deleteBook()` 回滚——**而这个方法已经被 installHooks 包过了**。于是「回滚」本身变成一次删除请求 → 也失败 → 又走 `restoreBook` 把书放回来。结果本地剩一本、`failed` 计数变 2、报错文案显示成「删除」。

修法：`installHooks` 时把原始方法存进 `origMethods`，**回滚一律走原始方法**。

> 一句话记住：**回滚动作不能让监听器看见。** 这是所有「先乐观写入、失败再撤」的设计都躲不开的坑。

### 9.3 为什么**故意没有**自动启动

现在打开页面，同步**不会自己开始**，必须在控制台手动 `Sync.enable()`。

这不是没做完，是不敢：一旦自动启动，每次打开页面都会先 `fetchAll()` 再 `replaceBooks()`。
**如果你还没跑过迁移，这一步会直接把你本地那几本书覆盖掉。**

所以顺序必须是：
1. 先手动迁移（第 8.3 节），确认书和笔记都在
2. 再打开实时同步：

```js
Sync.enable();
Sync.installHooks();
Sync.isMigrated();   // 应该是 true
```

3. 之后增删改一次，去另一台设备刷新，看有没有跟上

**自动启动**等第 1、2 步都验过再开（那时代码里加一行就够，但现在加就是拿你的数据赌）。

### 9.4 这一版还没做的

| 缺口 | 影响 | 什么时候补 |
|---|---|---|
| **失败时界面无提示** | 断网时增删改会静默回滚，用户只看到 console，界面不会告诉他「没同步上」 | 下一版（横幅或 toast） |
| 刷新后接线失效 | 现在 `installHooks` 只在当次页面有效，刷新要重新执行 | 自动启动那一版一起解决 |
| 笔记仍不跨设备 | `/api/notes` 还是占位，笔记只在本地 | 第二步 |
