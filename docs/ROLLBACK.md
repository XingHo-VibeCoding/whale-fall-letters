# 回滚手册（ROLLBACK）

> 出事时的第一反应应该是**翻这一页**，不是回忆上次怎么做的。
> 最后更新：2026-10-21（Day 26，v1.0 发布 + 静态托管回退实操演练）

---

## 零、先分清：你到底要回滚什么

回滚不是一个动作，是**四件完全不同的事**。选错对象，越滚越糟。

| 层 | 出问题的表现 | 回滚对象 | 本章节 | 今天练过吗 |
|---|---|---|---|---|
| 前端静态文件 | 页面白屏、按钮点了没反应、样式崩了 | 静态托管上的五个文件 | [一](#一静态托管回滚练过) | ✅ **实操过** |
| 云函数 | 接口全 500 / 返回字段对不上 / 改完接口就挂 | `books` 函数代码 | [二](#二云函数回滚只写在册未实操) | ❌ 只写在册 |
| 数据库结构 | 报 `column xxx does not exist`、整页读不出数据 | 表结构（迁移脚本） | [三](#三数据库回滚只写在册未实操) | ❌ 只写在册 |
| 数据内容 | 书被误删、笔记消失、数据写坏了 | 行数据本身 | [四](#四数据回滚只写在册未实操) | ❌ 只写在册 |

**判断顺序**：先看浏览器控制台报什么错 → 报 `xxx is not defined` / 白屏 = 前端；报 `HTTP 500` / 接口字段不对 = 云函数；报 `does not exist` = 数据库结构；数据凭空少了 = 数据层。

## 一、静态托管回滚（练过）

### 1.1 为什么这层最容易出事

因为**它的上线方式最不设防**：

```
git push  →  GitHub Pages 自动更新  →  ✅ 跟着走
git push  →  静态托管           →  ❌ 一动不动，必须手动上传
```

Day 24 血案：本地改了、提交了、推送了、`git log` 漂漂亮亮，**线上还停在 Day 17**（115,389 字节，还带旧文案）。所以「提交了」和「上线了」是两件事。

### 1.2 演练实测：两个数字，一个真一个假

| 演练 | 起止时刻 | 计时器读数 | 这个数字能信吗 |
|---|---|---|---|
| 回退 v1.0 → Day 23 | 16:00:16 → 16:10:59 | **643.6 秒**（10.73 分钟） | ❌ **不能**。含两次操作失误 |
| 恢复 Day 23 → v1.0 | 16:12:29 → 16:13:37 | **67.8 秒**（1.13 分钟） | ✅ 基本可信，一次干净操作 |

**那 643 秒里发生了什么**（如实记录，不粉饰）：

| 时刻 | 动作 | 结果 |
|---|---|---|
| 16:00:16 | 计时开始，去控制台上传 `community.js` | — |
| 16:03:06 | 上传完成，`last-modified` 更新 | ❌ 字节数没变（117,465），**传成了 v1.0 自己** |
| 16:03–16:09 | 排查：拉线上哈希、看响应头、比对目录 | 定位到「两个目录里都有同名 `community.js`」 |
| 16:09 | 准备重传 | ❌ 点成「上传**文件夹**」弹窗，文件根本不显示 |
| 16:10:59 | 改用「上传文件」重传 | ✅ 线上变 114,691 / `eca49f38` |

**结论（这条最重要）**：真出事时，你大概率**不会**在 68 秒内解决。今天 643 秒里有 610 秒是「点错 + 不知道错在哪」。**技术耗时是 68 秒，人的耗时是 10 分钟。** 手册的唯一作用是把这个差距压下来。

### 1.3 操作步骤（照做，别改顺序）

**准备（出事前就该做好，别等出事才找文件）**：

```
工作区根\day26-verify\rollback-kit\    <-- 注意：在工作区根，不在仓库内
  ├─ v1.0\     <- 当前正式版的五个文件（community.js 是 117465 / e685c37a）
  ├─ day23\    <- 上一版的五个文件（community.js 是 114691 / eca49f38）
  └─ manifest.txt  <- 每个文件的字节数 + SHA256 前 16 位
```

⚠️ **长期保存建议**：这个套件目前在 `day26-verify/`（临时验证目录，不进仓库）。真正的「出事能找回」备份应该**另存一份到仓库外的地方**（比如 U 盘、网盘），否则某天清理临时目录时可能一起删掉。至少要把 `manifest.txt` 里的哈希抄一份存着。

**执行**：

1. 打开控制台 → 云开发 CloudBase → 环境 `reading-sea` → **静态网站托管** → **文件管理**
2. 确认在**根目录**（不是 `assets/`、不是 `cloud-admin/` 等子目录）
3. 点「**上传**」按钮
4. ⚠️ 选「**上传文件**」，**不是**「上传文件夹」
   - 判据：标题栏写「选择要上传的**文件**」才是对的；写「选择要上传的**文件夹**」就是点错了，文件列表会是空的
5. 在文件选择框地址栏**粘贴完整路径**（不要一层层点目录，容易点错版本）：
   ```
   C:\Users\张俊\WorkBuddy\my-project\day26-verify\UPLOAD-DAY23\community.js
   ```
6. 确认覆盖

### 1.4 三步自证：怎么确认「真的换了」

**别相信「上传成功」四个字。** 用这三步，每一步都有数字：

| 步 | 看哪里 | v1.0（现在） | Day 23（回退目标） |
|---|---|---|---|
| ① 控制台大小 | 文件管理列表的「大小」列 | **114.71 KB** | **112.00 KB** |
| ② 线上字节 | `curl` 下载后 `wc -c` | **117,465** | **114,691** |
| ③ 线上哈希 | 去 CR 后 `sha256sum` | `e685c37aa5a2aae5` | `eca49f38b9b7e6ad` |

一段可复制的检查命令（在 git-bash 里跑）：

```bash
BASE="https://reading-sea-d7gd8l7o78b7304ae-1385227197.tcloudbaseapp.com"
curl -sS --ssl-no-revoke -o /tmp/live.js "$BASE/community.js?x=$(date +%s%N)"
echo "字节: $(wc -c < /tmp/live.js)"
echo "哈希: $(tr -d '\r' < /tmp/live.js | sha256sum | cut -c1-16)"
```

⚠️ **那个 `?x=$(date +%s%N)` 不能省**。它是防缓存的随机参数，省掉可能读到 CDN 旧副本，误判「没生效」然后重复上传。

⚠️ **比哈希前必须 `tr -d '\r'`**。本地是 CRLF、线上是 LF，原始字节数会差「行数」那么多（`index.html` 差 942 = 942 行），看起来像换错了，其实内容一样。

### 1.5 计时器（可选，但建议用）

`day26-verify/rollback-timer.js` 会在你操作时每 3 秒探测线上哈希，捕捉到变化那一刻自动算出耗时：

```bash
node ../day26-verify/rollback-timer.js --to day23   # 等线上变成 Day 23 版
node ../day26-verify/rollback-timer.js --to v1.0    # 等线上变回 v1.0
```

它会先打印「当前线上是什么」，如果已经是目标版本就直接拒绝——**防止你等一个本来就已经实现的状态**。

## 二、云函数回滚（只写在册，未实操）

> ⚠️ **本章的步骤没有在本项目实操验证过**，是按 Day 19 的部署流程推导的。真要用之前先拿一个无关紧要的函数试一遍。

### 2.1 先判断：是函数的问题吗

| 现象 | 大概率是 |
|---|---|
| `/api/books` 返回 `INVALID_PATH` | **网关**配置，不是函数（测的是网关） |
| 返回 `INVALID_ENV` | **环境 ID 抄错了**（Day 17 血案，先核 ID 再怀疑平台） |
| `HTTP 500` + 空响应 | 函数代码崩了 |
| `HTTP 200` + `{ok:false, error:"..."}` | **业务失败，是正常契约**，不是函数挂了 |
| 返回字段少了/名字不对 | 函数版本不对，或迁移没跑 |

### 2.2 回滚步骤

1. 控制台 → 云开发 → 云函数 → `books` → **函数代码**
2. 用**在线 IDE** 打开 `index.js` / `db.js`
3. 把内容替换成上一个可用版本（从 git 取）：
   ```bash
   cd whale-fall-letters
   git show <上一个可用提交>:cloud/functions/books/index.js > /tmp/index.js
   git show <上一个可用提交>:cloud/functions/books/db.js > /tmp/db.js
   ```
4. Ctrl+S 保存，点 IDE 的「**部署**」
5. 提示「无 package.json 无法装依赖」→ 选「**部署且不安装依赖**」（本项目零依赖）

⚠️ **不要用「上传代码」zip 包**。多文件函数整包替换会丢掉平台自动生成的 `scf_bootstrap`，报 `filename not matched: scf_bootstrap`，函数再也起不来。

### 2.3 自证

探针**必须走网关已映射的 `/api/books` 前缀**：

```bash
curl -sS --ssl-no-revoke "https://reading-sea-d7gd8l7o78b7304ae.service.tcloudbase.com/api/books/book-001"
```

看返回文案判断版本（比如软删除新版会带 `softDeleted` 相关行为）。用 `/api/no-such-path` 测出来的是网关，不是函数。

## 三、数据库回滚（只写在册，未实操）

> ⚠️ 未实操。**这一层风险最高**——删列、改类型可能直接丢数据。

### 3.1 铁律：顺序不能反

```
加字段类迁移：先跑 SQL  →  再部署函数     ← 对的
              先部署函数 →  跑 SQL        ← ❌ 报 column does not exist，整页读不出数据
```

反了会怎样：函数里 `SELECT` 了 `is_deleted`，但表里没这列 → PG 直接报错 → 接口 500 → 检查台整页空白。Day 23 就是这么差点翻车的。

### 3.2 回滚步骤（加字段类，可安全回退）

1. 控制台 → 云开发 → 数据库 → **SQL 编辑器**
2. 先**备份**（这一步别省）：
   ```sql
   CREATE TABLE books_backup_20261021 AS SELECT * FROM books;
   ```
3. 回滚列：
   ```sql
   ALTER TABLE books DROP COLUMN IF EXISTS "is_deleted";
   ```
4. 同步回滚**函数代码**（见第二节），否则函数还在查不存在的列

### 3.3 自证

```sql
SELECT column_name FROM information_schema.columns
WHERE table_name = 'books' ORDER BY ordinal_position;
```

字段数要对得上（Day 24 实测是 11 个字段）。

## 四、数据回滚（只写在册，未实操）

> ⚠️ 未实操。**依赖 Day 23 的软删除设计，没有它就只能靠备份。**

### 4.1 幸好当初没硬删

Day 23 把 DELETE 改成了软删除：`books.is_deleted = true`，**行还在表里，只是查询时被过滤掉**。而且**笔记故意没删**——恢复时一并回来。

所以「删错一本书」是可救的：

```sql
-- 先确认它还在
SELECT id, title, "is_deleted", "createdAt" FROM books WHERE title LIKE '%书名%';

-- 捞回来
UPDATE books SET "is_deleted" = false WHERE id = 'book-xxxx';
```

⚠️ 返回字段是 `is_deleted`（**下划线**），不是驼峰。这是历史遗留的不统一，写 SQL 时别按直觉敲成 `"isDeleted"`。

### 4.2 硬删了怎么办

硬删（`DELETE FROM books`）**没有后悔药**，只能靠：

| 手段 | 前提 | 本项目现状 |
|---|---|---|
| 数据库备份 | 建过备份/自动备份 | ❌ 没配 |
| 建表快照 | 出事前 `CREATE TABLE ... AS SELECT` | ❌ 平时没做 |
| 重新灌种子数据 | `db/seed.sql` 还在 | ✅ 只能回到 5 本样书，真数据没了 |

**这条是今天最大的收获：软删除不是「多写几行代码」，是「出事时还有没有第二次机会」。**

## 五、什么情况必须回滚（判断表）

> 先看这张表，再决定动不动手。**回滚本身有风险**，不该滚的时候滚，会把小问题放大。

### 5.1 立刻回滚（不等，先止血）

| 情况 | 为什么不能等 | 先滚哪一层 |
|---|---|---|
| 页面**白屏** / 完全打不开 | 100% 用户受影响，等于停服 | 前端静态文件 |
| 控制台报 `Uncaught ReferenceError` 且是刚改的文件 | 前端代码出错，整站 JS 停摆 | 前端静态文件 |
| 首页能开但**所有按钮无响应** | 同上，交互全废 | 前端静态文件 |
| 样式彻底崩坏（黑底黑字、元素叠成一团） | 无法阅读，等于不可用 | 前端静态文件 |
| 接口**全部** 500 | 有依赖接口的功能全废 | 云函数 |
| 报 `column xxx does not exist` | 迁移与代码错位，读写全挂 | 数据库 + 云函数 |
| 用户数据**正在被写坏**（如误删批量数据） | 每多一秒损失更多 | 数据层，同时停掉写入 |

### 5.2 观察，不急着滚

| 情况 | 为什么不急 | 该做什么 |
|---|---|---|
| 单个按钮报错，其他功能正常 | 影响面小，回滚可能引入新问题 | 记下来，当天修 |
| 某条文案错别字 | 不影响功能 | 攒着下次一起发 |
| 接口返回 `{ok:false}` 但页面有友好提示 | **这是正常契约，不是故障** | 查业务逻辑，别回滚 |
| 某个字段返回了 `null` | 可能是数据本身为空 | 先查库确认 |
| 只在**某个浏览器**上不对 | 大概率兼容问题，不是版本问题 | 换浏览器复现，别急着滚 |
| 只有**你本机**不对 | 大概率是你本地缓存/localStorage | 先 `Ctrl+Shift+R` 硬刷新、清 localStorage |

### 5.3 别回滚，去修

| 情况 | 为什么 |
|---|---|
| 问题出在**网关配置**（`INVALID_PATH`、跨域白名单） | 回滚代码一点用没有，得改控制台配置 |
| 问题出在 **DNS/域名**（`INVALID_ENV`） | 先核对环境 ID 有没有抄错（Day 17 血案：l 抄成 i，查了两周） |
| 数据本身错了，代码没问题 | 回滚代码只会让错误数据继续被错误地渲染 |
| 你**说不清**故障现象 | 先复现、先定位。**乱滚 = 把现场破坏了** |

### 5.4 回滚前必须问自己的三个问题

1. **故障是「刚才这次发布」引入的吗？** —— 不是的话，回滚到上一版**解决不了问题**，只是把两个问题叠在一起。
2. **我能说清回滚到哪个版本吗？** —— 说不清就先去 `git log` / `manifest.txt` 查清楚目标哈希。
3. **回滚后怎么确认成功了？** —— 说不出验证方法，就不要开始。回滚完发现「还是坏的」，你会分不清是回滚失败还是原问题没解决。

## 六、这份手册自己踩过的坑

| # | 坑 | 真相 |
|---|---|---|
| 1 | 两个目录里都有 `community.js`，选文件时看走眼 | 传成了「当前版」自己，字节数不变，白折腾 10 分钟。**对策：待传文件单独放一个目录，目录里只放那一个文件** |
| 2 | 点「上传」后弹的是「上传文件夹」 | 文件列表永远空。**看标题栏文字确认**，写「文件夹」就是错了 |
| 3 | 控制台显示 `114.71 KB`，文件是 117,465 字节 | 控制台按 1024 换算。**换算表要对上，别拿 KB 和字节直接比** |
| 4 | 本地 120,448 / 线上 117,465，差 2,983 | 2,983 = 该文件行数，是 CRLF/LF 差异。**比哈希前先 `tr -d '\r'`** |
| 5 | 改完一个前端文件，preflight 第 4 条报红 | 检查脚本自己的口径 bug（字节数没去 CR）。Day 26 已修，并做了反向验证 |
| 6 | `stdbuf` 在 Windows 上报 `libstdbuf.dll` 找不到 | Windows 的 git-bash 没有这玩意。**别用它**，直接把输出重定向到日志文件 |
| 7 | 回滚是静态托管操作，**不产生 git 提交** | 所以「回滚前后的提交记录」截图，截的是版本标记（tag）和发布历史，不是回滚动作本身 |

## 七、出事时的 60 秒流程（贴在墙上）

```
第 1 步（10 秒）打开页面，看是「白屏」还是「能开但报错」
第 2 步（10 秒）F12 看控制台第一行红字
                 ├─ xxx is not defined / 白屏      → 前端，翻第一节
                 ├─ HTTP 500 / 字段不对            → 云函数，翻第二节
                 └─ column xxx does not exist      → 数据库，翻第三节
第 3 步（20 秒）问自己三件事：是这次发布引入的吗？目标版本是哪个？怎么验成功？
第 4 步（20 秒）翻第五节判断表：立刻滚 / 观察 / 别滚
```

**别跳过第 3 步。** 今天演练 643 秒 vs 68 秒的差距，全部来自「没想清楚就开始动手」。
