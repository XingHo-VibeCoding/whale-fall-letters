> 「完整走两遍『写入 → 刷新 → 持久化 → 修改 → 删除』，两遍结果一致 = 可重复完成；**只成功一遍 = 还不算能交付**。」

> | 接口层 | PostgreSQL（`/api/books` 四个方法） | 重新发一次 HTTP 请求，服务端不认识「上一次请求」 | 本文第 2 节的原始记录 |

### 这个脚本怎么做到「真」

- 用的是仓库里**真的 `store.js`**，不复制、不改写一行
- 「刷新」= `vm.createContext()` 新建一个上下文，把上一轮的所有内存变量（含 `Store` 实例）全部丢掉，只把 localStorage 的内容带过去。这跟 F5 的语义一致
- 每轮从**空存储**开始，两轮条件完全相同
- 31 个断言、零依赖（只用 Node 内置 `vm` / `fs` / `path`），`git clone` 下来就能跑

### 两轮为什么不能做字节级对比

`id` 是 `前缀_时间戳36进制+随机6位`，时间戳是 `new Date()`。两轮 id 必然不同。
所以比的是**行为等价**：每步成败、字段取值、刷新后可见性，以及最终存储在「抹掉 id 与时间戳后」是否完全相同。
把 id 抹掉再比，比硬凑出一模一样的两轮更有意义——**真实使用中 id 本来就该不同**。

### 这里抓到一次「我以为是 bug」

第一次跑，两轮都红在同一步：`刷新后：书已消失`。

两轮红得**一模一样**，说明不是随机故障。查 `store.js:227` 的注释：

```js
/** 按 id 取一本书。找不到返回 data:null（不是错误）。 */
```

**是我的断言写错了**（我以为找不到 = `ok:false`），代码行为是设计好的。
改断言后 31/31 全绿。

> 这件事本身值得记：**误报和漏报一样坏**。如果我当时直接去改 `store.js`「修 bug」，
> 就把一个正常行为改坏了——而这正是「两轮都红」这个信号救下来的：
> 它证明这是稳定行为，不是偶发。

### 顺带发现一处前后端语义不一致（记成技术债，今天不改）

同一个「这本书不存在」：

| 位置 | 返回 |
|---|---|
| 前端 `store.getBook()` | `{ ok: true, data: null }` |
| 后端 `PATCH /api/books/:id` | `{ ok: false, error: "这本书不存在，可能已被删除" }` |

两边各有各的道理（前端把「没查到」当正常状态，后端把「改不存在的书」当错误），
但**同一项目里两套表达**，将来接真库时这里一定会有人写错一次。已记入第 7 节技术债。

### 说明

- **每轮结束都核对总条数**：跑之前 5 本，跑完还是 5 本，没有遗留垃圾数据
- **第 7 步是故意多做的**：重复删除必须报「不存在」，不能谎报成功。
  如果只测「删除成功」，那「删两次都返回 deletedBooks:1」这种谎报就永远测不出来

  同一操作两轮相差在 0.06–0.12s，属正常网络波动，不是「时好时坏」
- 业务失败一律 HTTP 200 + `ok:false`（`send()` 固定 `writeHead(200)`），所以上表同时记 `http` 和 `ok`

## 3. 本次没覆盖到的（说清楚，不含糊）

| 没测什么 | 为什么 | 风险 |
|---|---|---|
| 并发写入 | 单人项目，两轮都是顺序执行 | 同一秒连点两次「添加」可能进两条（前端有 AC-2 的空值校验，但没有去重闸门） |
| 网络中断时的表现 | 需要断网工具，今天没做 | 接口层会走 `describeApiError()` 显示可读错误；前端 localStorage 层不受影响 |
