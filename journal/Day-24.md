## 二、今日要掌握：怎么排除掉其他原因、锁定真正原因

### 现象

「接口数据」页先正常抓到 5 本书，然后让接口失败，点页面里的「刷新」——**状态栏变红说「读不到」，下面 5 本书照旧摆着，表格一点变化都没有**。

用户看到的是：一个正在报错、同时又在展示数据的页面。分不清这数据是刚抓的还是三天前的。

### 排除法：8 个嫌疑，排掉 7 个

| # | 怀疑对象 | 怎么排除的 | 证据 |
|---|---|---|---|
| 1 | 大帅断网了 | 恢复网络后同页面立刻正常；13 个静态请求全 200 | 截图恢复后「真库返回 5 本书」 |
| 2 | 云函数挂了 | `curl` 直连接口 | `HTTP=200`，1.28 s |
| 3 | 数据库/数据源坏了 | 看 curl 返回内容 | 5 本真书，书名作者对得上 |
| 4 | 跨域被浏览器拦 | 带本站 Origin 重发 | 响应有 `access-control-allow-origin: https://reading-sea-…tcloudbaseapp.com` |
| 5 | 网关/域名/路由错 | 同一路径直连 | 200 |
| 6 | 请求失败根本没被识别 | 看状态栏 | 确实变红、带 `is-error` → **错误分支跑到了** |
| 7 | 文案写错了 | 读 `describeApiError` | 断网时说「网络连不上」是实话 |
| 8 | **渲染层没把「失败」和「旧数据」对齐** | 排除完只剩它 | 见下 |

**第 6 条是转折点**：如果错误分支压根没跑，问题是「没接住异常」；它跑了、也变红了，说明接住了、**只是接住之后做的事不完整**——处理范围从「整个页面」缩到了「状态栏这一个节点」。这一步把嫌疑整体从「网络类」推到「渲染类」。

### 真因钉在代码上

`community.js` 的 `loadApiDemo()` 失败分支，改之前是这样的：

```js
      .catch(function (err) {
        if (window.console && window.console.error) {
          window.console.error('[api-demo] 原始错误（只给自己排查用）：', err);
        }
        setStatus(describeApiError(err), true);   // ← 只改状态栏这一行字
      });                                          // ← 表格一个字节都没动
```

而「进入页面」时是清了的（`enterApiDemo()` 有 `t.textContent = ''`）。所以：**只有「进页面」会清表格，「刷新失败」不会。** 上一轮渲染的 `<table>` 原样留在 DOM 里。

### 因果验证：只改一个变量

不是「看着像」，是控制变量：

| 组 | 操作 | 失败后屏幕上还有几本书 |
|---|---|---|
| A（现状） | 成功 → 断网 → 刷新 | **5 本（残留）** |
| B（对照） | 成功 → **清空表格** → 断网 → 刷新 | **0 本（已清）** |

唯一变量是「失败前有没有清空 `#api-demo-table`」，结果完全不同 → 残留的原因只能是「没清空」，跟网络、接口、跨域、CSS 全都无关。脚本：`day24-verify/locate-causal.js`。

## 三、四步证据

### ① 复现

**大帅（真站，断网）**：`journal/assets/Day-24-repro-console.jpg`
地址栏 `…tcloudbaseapp.com/#/api-demo` + 红字「接口暂时读不到: Failed to fetch（本地书单不受影响）」+ 5 本书还在 + 控制台 `GET …/api/books net::ERR_INTERNET_DISCONNECTED`。

**我（自动化，跑真代码路径）**：`day24-verify/repro-api-demo.js`

```
状态栏 is-error：true
表格里还剩几本书：5
❌ 复现成功：页面同时说着"出错了"和摆着 5 本书，用户没法判断哪个是真的。
```

### ② 定位

见第二节。`day24-verify/locate-causal.js` 输出：

```
A 组（现状，不清空）：失败轮：屏幕上仍有 5 本书  ← 残留
B 组（清了再失败）  ：失败轮：屏幕上仍有 0 本书  ← 已清
✅ A 残留、B 不残留 → 唯一变量「有没有清空表格」决定了结果。
```

### ③ 修复

`community.js` 三处，共 +47 / −2：

1. 新增 `markApiDemoStale(reason)`：靠 **DOM 里有没有 `<table>`** 判断有没有旧数据（不看内部变量，渲染结果才是事实）
   - 没旧数据 → 只报错，不做多余标记
   - 有旧数据 → 表格 `opacity = 0.45` 灰下去 + 状态栏追加「｜下面显示的是上次 HH:MM:SS 抓到的旧数据，可能已过期」
2. 失败分支 `setStatus(...)` → `markApiDemoStale(...)`
3. 成功渲染时把 `opacity` 复位、记下成功时刻 `apiDemoLastOkClock`

**方案取舍（A vs B）**：
- A 失败就清空表格 —— 简单，但用户刚看到的数据就没了
- **B 保留数据 + 标记过期**（采用）—— 数据本身有价值（这页就是「看真库有什么」），但必须一眼看出它是旧的
- 不加新 CSS、不加新颜色，只用内联 `opacity` + 已有 `.is-error`，改动面最小、回滚只需还原一个函数和它的调用点

## 四、今天最大的意外：代码提交不等于线上生效

排查中途发现：**CloudBase 静态托管上的 `community.js` 停在 Day 17 那一版**。

客观证据（不靠描述，靠 curl 逐字节比）：

| | 大小 | `markApiDemoStale` | 旧文案「接口暂时读不到」 |
|---|---|---|---|
| 上传前线上 | 115,389 字节 | 0 处 | 1 处 |
| 本地（修复后） | 120,448 字节 | 3 处 | 0 处 |
| 上传后线上 | 120,448 字节 | 3 处 | 0 处 |

`cmp` 比对：**与本地完全一致**。

**结论：静态托管是手动上传的，`git push` 不会带动它。** 所以线上其实落后仓库好几天：Day 23 的三类错误提示在前端一直没生效。同类问题还有一个——`GET /api/books` 返回的书里没有 `is_deleted` 字段，说明真库没跑 Day 23 的迁移 SQL、`books` 云函数也没部署新版，**软删除在线上等于不存在**。

**教训**：「提交了」「部署了」「推送成功」都是过程报告，不是事实。要验就去看线上那份文件本身。

## 七、一句话总结

**报错页面的第一职责不是「告诉用户出错」，而是「让用户能相信屏幕上剩下的东西」。** 数据可以旧，但不能假装新——今天修的从来不是网络，是这句话。
