| 失误 | 根因 | 事后看应该怎么避免 |
|---|---|---|

### 3.2 打 tag（annotated，不是轻量）

```bash
git tag -a v1.0 -m "Day 26｜发布 v1.0 正式版..."
```

`-a` 是附注标签，会存下**谁打的、什么时候打的、为什么打**。轻量标签只是一个指针，没有这些信息。发布正式版用附注标签，以后回看能知道当时在想什么。

### 3.4 上传 + 哈希核验

| 文件 | 线上字节 / 哈希 | 结果 |
|---|---|---|
| index.html | 55854 / `ea20780743e87ded` | ✅ MATCH |
| styles.css | 59991 / `69da8519326e791a` | ✅ MATCH |

| app.js | 30647 / `b9c41c0ea5326228` | ✅ MATCH |
| community.js | 117465 / `e685c37aa5a2aae5` | ✅ MATCH |

### 3.5 一个有价值的旁支：字节数不等 ≠ 内容不同

上传前线上 `index.html` 是 56,796 字节，上传后 55,854，**少了 942**。
`community.js` 从 120,448 变 117,465，**少了 2,983**。

这个差值恰好等于各自的行数：

```
index.html   942 行   → 差 942
community.js 2,983 行 → 差 2,983
```

原因：**本地工作区是 CRLF（`core.autocrlf=true`），线上是 LF**。每个换行少一个 `\r`。
去掉 CR 后五个文件哈希**完全一致**，内容没有任何区别。

这也是为什么一开始我会困惑：「工作区 `index.html` 是 56,796，git 里是 55,854，`git diff` 却干净」——因为 `autocrlf` 会在比对前自动归一化行尾。

**规矩记下来：判内容是否相同，一律用「去 CR 的哈希」，不要用原始字节数。**

## 四、回滚演练的取证方式

### 4.1 为什么不用秒表

秒表是人按的，误差大，而且**没法复核**——记录里写「花了 5 分钟」，谁也证明不了。

所以写了个计时器 `day26-verify/rollback-timer.js`：

- 记录开始时刻
- **每 3 秒**去 `curl` 线上 `community.js`，算「去 CR 哈希」
- 一旦哈希变成目标版本，立刻记结束时刻、算耗时
- 先打印「当前线上是什么」，如果已经是目标版本就**直接拒绝**——防止等一个本来就已经实现的状态

它量的是「线上文件真的变了」那一刻，有哈希做凭据。

### 4.2 写完先自测，不然它瞎了都不知道

自测时发现一个问题：**偶发探测返回 0 字节 / 空哈希**（网络抖动）。

这不会导致「误判成功」（空哈希匹配不上具体值），但会**少一个数据点**，让耗时记录偏慢。所以加了「立即重试一次」，仍然失败就明确标 `ok:false` 并继续轮询，不把它当成「还是旧版本」。

### 4.3 两次演练的完整记录

**第一次（回退，643.6 秒）**：

```
开始 16:00:16  线上 117465 / e685c37a
16:03:06       覆盖动作发生（last-modified 更新），但字节数仍是 117465  ← 传错
16:03-16:09    排查（拉哈希、看响应头、比对目录）
16:09          点成「上传文件夹」，文件列表空
16:10:59       改成「上传文件」重传成功
结束           线上 114691 / eca49f38   探测 156 次，失败 0 次
```

**第二次（恢复，67.8 秒）**：

```

16:13:37       线上 117465 / e685c37a   探测 16 次，失败 0 次
```

## 五、顺手修掉的一个检查脚本 bug

回滚恢复到 v1.0 后复跑 preflight，**第 4 条报红了**：

```
✗ FAIL 本地与线上不一致 3/5：index.html 本地 56796 / 线上 55854（差 -942 字节）…
```

但我一个前端文件都没改。查下来是**检查脚本自己的口径 bug**：

```js
// 原代码
if (got.bytes === localBuf.length && sha256NoCR(got.buf) === sha256NoCR(localBuf))
//     ↑ 字节数用原始长度（含 CR）    ↑ 哈希去掉 CR
```

两个口径不一致：本地 CRLF、线上 LF → 字节数必然差「行数」那么多，**哈希再相等也会被前面的字节数卡死**。

这是 Day 25 写这个脚本时就记下的待办「第 4 条行尾口径（CRLF 可能假红）」，今天**真实触发了第一次误报**。

修法：加一个 `lenNoCR()`，让字节数也走「去 CR」口径。

**改完必须做反向验证，否则它可能变成永远绿的摆设**：

| 步 | 动作 | 期望 | 实际 |
|---|---|---|---|
| 1 基线 | 修完直接跑 | 绿 | ✅ PASS（5/5 全等，合计 281333 字节） |
| 2 植入 | 改 `community.js` 一个字的文案，不上传 | 红 | ✅ FAIL（本地 117466 / 线上 117465，**差 -1 字节**） |
| 3 还原 | 恢复文件 | 绿 | ✅ PASS，`git diff` 0 行 |

**第 2 步最有说服力**：`sed` 处理后行尾从 CRLF 变成了 LF（120448 → 117466），但第 4 条仍然准确报出了那 **1 个字节**的真实差异，没有被行尾差异（2983 字节）淹没。这恰好证明新口径是对的。

## 六、今天真正学到的东西

### 6.1 「上传成功」和「上传对了」是两件事

三次证据都指向同一个模式：

| 场景 | 它说什么 | 真相 |
|---|---|---|
| `git commit` | `nothing to commit` | 提交其实建好了（Day 25 第 5 次复现） |
| 控制台 | 「上传成功」 | 传的是同名旧版本，字节数没变（今天） |
| preflight | 第 4 条 FAIL | 检查脚本自己有 bug（今天） |

**共同的解法**：不看它自己说什么，去看**能被独立复核的数字**。今天这个数字是「去 CR 后的 SHA256」。

### 6.2 软删除的价值，今天才真正看懂

`docs/ROLLBACK.md` 第四节写数据恢复时发现：

- **软删除**（Day 23 做的）：删错一本书，`UPDATE ... SET is_deleted = false` 就捞回来了，笔记还一并回来（当初故意没删）
- **硬删除**：没有后悔药。本项目**没配数据库备份**，`db/seed.sql` 只能回到 5 本样书，真数据全没

**软删除不是「多写几行代码」，是「出事时还有没有第二次机会」。** 当初做的时候只是当成一个技术点，今天站在「回滚手册」的角度看，它是一条命。

### 6.3 回滚本身有风险

写「什么情况必须回滚」判断表时想清楚一件事：**不该滚的时候滚，会把小问题放大**。

所以 `docs/ROLLBACK.md` 第五节分了三档：

- **立刻回滚**：白屏、所有按钮失灵、接口全 500、报 `column does not exist`
- **观察不急着滚**：单个按钮报错、文案错别字、只在你本机不对（先清缓存）
- **别回滚，去修**：网关配置问题、环境 ID 抄错、数据本身错了、**你说不清故障现象**

最后一条最重要：**说不清故障就乱滚，等于把现场破坏了**，事后查不出真因。
